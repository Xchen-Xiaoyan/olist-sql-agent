# 评测报告：数据分析 Agent 什么时候值得用

**一句话结论**：强模型（Gemini 3.5 flash-lite）直接写一次 SQL 已经能答对 96% 的问题，Agent 只多答对 1 题。它在强模型上的价值主要是**出错后能自己改**、**每一步都可查看**、**能画图、能追问**，代价是延迟从 0.7 秒增加到 2.0 秒。
弱的本地模型（qwen2.5 7B）受益最大：答对率从 52% 提高到 66%。但它在"该不该反问"这类判断上反而变差了。

## 1. 评测设计

- **题目**：60 道，全部由我手写，并附标准 SQL，每条标准 SQL 都运行验证过（[questions.py](questions.py)）。
  - **单表聚合（10 题）**：如"平台有多少有效订单"。
  - **多表关联（10 题）**：如"GMV 前 5 的品类"。
  - **时间（8 题）**：环比、同比、按季度、按星期。
  - **指标口径（8 题）**：不按口径就会算错的题，比如买家要去重、准时率只看已送达订单、GMV 只算有效订单。
  - **多步（6 题）**：头部 10% 卖家的 GMV 占比、带门槛的排名、同期群留存、同比增速排名。
  - **查值（8 题）**：用户的说法和库里存的值不一样，必须先查到实际值才能写对。例如"圣保罗市"在库里是 `sao paulo`，模糊匹配会混进 `sao paulo das missoes` 等其他城市；"手机"在库里是 `telephony`。
  - **应反问（5 题）**：没说清用哪个指标，如"哪个卖家最好"。
  - **应拒答（5 题）**：数据里没有，如利润率、用户年龄、2019 年的数据。
- **判分**（[compare.py](compare.py)）：
  - **答案正确（主指标）**：满足下面任意一条即算对。
    - 最终查询的结果表与标准答案一致。
    - 或者文字回答里给出了标准答案的数值和名称。这一条只对结果不超过 3 行的题生效。
      - 数值必须是标准答案按回答所写的精度四舍五入后的结果。例如写"117.3 万"，真实值要在 117.25 万到 117.35 万之间；写"165.36"，就必须正好是 165.36。
      - 写法的精度要有意义：舍入单位不能超过真实值的 1%，所以整数"1"不能算作 1.40。
      - "2017年1月"里的数字是日期，不当作答案。
      - 支持"万""亿""%"和千分位等写法。
  - **结果表精确匹配**：只比较结果表。
    - 不看行的顺序，允许多出列。
    - 计数必须完全相等，其他数值允许 0.1% 误差，或四舍五入到 2 位小数以上。
  - **为什么要两个指标**：Agent 经常返回比问题更完整的表（比如列出全部月份），再在文字里点出答案，这对用户来说是对的。只看结果表会低估它，所以两个都报。
  - **人工复核**：只靠文本匹配判为正确的 14 个回答，我逐条看过，都是真的答对了。复核过程中发现过 3 个误判：两个数值偏差 0.3% 的错答案，被最初 0.6% 的容差放过了；还有一个回答写"增长率为 0%"，却因为"2017年1月"里的"1"被判对。为此收紧了上面的规则，然后全部重判。
- **对比的三种方式**：
  - **Baseline**：同一份数据字典，模型一次写出一条 SQL，执行一次，没有任何反馈。它也可以回复 `CLARIFY:` 反问，或 `DECLINE:` 拒答。
  - **Agent v1**：工具调用循环，四个工具是 `run_sql`、`make_chart`、`ask_clarification`、`decline`。SQL 报错会回传给模型，最多 8 步；如果没查数据就想作答，会被要求先查。
  - **Agent v2**：在 v1 基础上加两条规则。
    - 过滤条件用到数据字典里没写的值时，先查出实际存的值。
    - 写最终查询前对照清单自查：有没有过滤有效订单？度量（件数、金额、均值、比率）对不对？配送类指标是否只看已送达订单？
- **模型**：
  - Gemini 3.5 flash-lite，免费额度。
  - qwen2.5:7b，通过 Ollama 在本机 RTX 5060 8GB 上运行。
  - 温度都设为 0，每题跑一次。
  - gemini-3.5-flash 免费额度每天只有 20 次请求，不够跑完评测，所以没有纳入。
- **延迟**：只计模型调用和 SQL 执行的时间，不含为遵守免费额度限速而等待的时间。

## 2. 结果

| 模型 | 方式 | 答案正确（50 道数据题） | 结果表精确匹配 | 单表 | 多表 | 时间 | 口径 | 多步 | 查值 | 反问 (5) | 拒答 (5) |
|---|---|---|---|---|---|---|---|---|---|---|---|
| Gemini flash-lite | Baseline | 96% | 96% | 100% | 100% | 100% | 88% | 100% | 88% | 100% | 100% |
| Gemini flash-lite | **Agent v2** | **98%** | 84% | 100% | 100% | 100% | 100% | 100% | 88% | 100% | 100% |
| qwen2.5 7B | Baseline | 52% | 52% | 100% | 50% | 25% | 88% | 17% | 12% | 100% | 100% |
| qwen2.5 7B | Agent v1 | 62% | 60% | 80% | 70% | 50% | 88% | 50% | 25% | 60% | 60% |
| qwen2.5 7B | **Agent v2** | **66%** | 64% | 90% | 90% | 50% | 88% | 33% | 25% | 40% | 80% |

Agent v1 在 Gemini 上只跑了前 52 题（查值类题目是之后才加的），这 52 题全部答对；Agent v2 在这 52 题上也是全对。

| 模型 | 方式 | SQL 报错的题 | 报错后自己改对 | 模型调用次数/题 | 延迟中位数 | 延迟 p90 |
|---|---|---|---|---|---|---|
| Gemini flash-lite | Baseline | 0 / 50 | — | 1.0 | 0.7 s | 1.1 s |
| Gemini flash-lite | Agent v1 | 4 / 42 | **4 / 4** | 2.3 | 2.0 s | 3.0 s |

所有配置都没有出现"对能回答的数据题错误地反问或拒答"。

## 3. 发现

**① 强模型 + 好的数据字典，单次生成已经很准。** Gemini 的 Baseline 只错了 2 题：
- m01："有多少买家"没有去重。
- e03：见 ⑥。

Agent 修好了 m01。50 道题里 1 道题就是 2 个百分点，所以 96% 和 98% 之间**不能说有显著差别**。这说明对干净的星型模型来说，**数据字典和指标口径写得好不好，比有没有 Agent 更关键**。

**② Agent 的价值在可靠性和透明度，而不只是准确率。**
- **出错能自己改**：Gemini Agent 报错的 5 道题全部改对了。典型例子是用了不存在的列 `year_month`：DuckDB 报错时会提示可能的列名，Agent 读到后改用 `dim_date` 关联，下一步就成功了。而 Baseline 一旦报错只能直接失败。
- **反问和拒答都是 100%**。
- **每一步都能查看**：每条 SQL、每次报错都展示在页面上。
- **能画图、能多轮追问**。
- **代价**：每题多 1.3 次模型调用，延迟中位数从 0.7 秒增加到 2.0 秒。

**③ 弱模型受益最大，提升主要来自多表关联和时间题。**
- qwen 7B 整体从 52% 提高到 66%。
- 多表关联从 50% 到 90%，时间题从 25% 到 50%。
- Baseline 的 12 次 SQL 报错全部直接失败；Agent 能把其中一部分改对。

**④ 小模型做"判断"反而变差了，这是这次最意外的结果。**
- qwen 的 Baseline 反问和拒答都是 100%，加上工具后反问降到 40%。
- 原因一：问题不清楚时，它会自己挑一个指标（比如按销售额）直接回答，而不是反问。
- 原因二：有时把工具调用写成一段文字，比如回复 `decline {"reason": ...}`，而不是真的调用工具。
- **结论**：线上 demo 用 Gemini。如果要用小模型，应该先单独做一步意图分类（数据题、需要反问、需要拒答），再进入工具循环；同时要能解析写成文字的工具调用。

**⑤ v1 → v2 的规则对 Gemini 有效，对 qwen 帮助有限。**
- v2 的 Gemini 在 8 道查值题上**全部先查了实际存的值**，例如 `SELECT DISTINCT city ... ILIKE '%curitiba%'`，再用精确值过滤。
- 但 Gemini 在这些题上准确率没变：数据字典里写明了"城市名是小写、不带重音"，它原本就能猜对。
- qwen 从 62% 到 66%，只多对 2 题，在 50 道题上不算显著。能力上限主要取决于模型本身。

**⑥ 两个模型都错在同一题，问题出在题目口径。**
- e03 问"所有图书类品类的 GMV"。两个模型都用了数据字典里的品类大类"文娱图书"，而这个大类还包括音乐、文具、艺术品。
- 标准答案只算 3 个 `books_*` 品类。
- Gemini Agent 在回答里写明了"文娱图书类（包含大众图书、专业图书、进口图书、文具、艺术、乐器等）"，用户能看出口径不同；Baseline 只给一个数字。
- 真实场景里，这类题应该反问或者说明假设。

## 4. 局限

- **题量小**：只有 50 道数据题，1 题 = 2 个百分点。每个配置只跑一次（温度 0），没有做多次运行的方差估计。
- **题目有作者偏差**：题目和标准答案都是我写的，可能偏向我自己对口径的理解。
- **文本匹配是近似的**：判为正确的题已经人工复核过，但它没有覆盖结果超过 3 行的题。
- **数据集很干净**：只有一个已清洗好的星型模型。真实业务库里表和字段更多、命名更乱，查值和纠错的价值应该更大，但这次没有测到。

## 5. 复现

```bash
python scripts/build_db.py                       # 由 olist-bi-dashboard 的清洗结果生成 data/olist.duckdb
python eval/run_eval.py --system baseline --provider gemini --model gemini-3.5-flash-lite --workers 2
python eval/run_eval.py --system agent    --provider gemini --model gemini-3.5-flash-lite --workers 2
python eval/run_eval.py --system baseline --provider ollama --model qwen2.5:7b
python eval/run_eval.py --system agent    --provider ollama --model qwen2.5:7b
python eval/regrade.py                           # 修改判分规则后重判，不需要调用模型
python eval/summarize.py
```

每题的完整步骤（每条 SQL、报错、模型调用次数、耗时）都保存在 `eval/results/*.jsonl`。
